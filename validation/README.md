# 測定モデルとしての検証（validation/）

このディレクトリは、`src/lib/engine` を **測定器として** 検証するための実験一式です。
アプリが動くかではなく、**アプリが出す数字が何かを測っているか** を調べます。

```bash
npm run validate     # 10実験を実行し validation/report/ に出力（約20秒・API不要）
```

この検証で見つかった欠陥のうち3つは、すでに修正されています（README §12 の #12）。
本文の「修正前」はコミット `29ce724` 時点、「現在」は同じ実験・同じシードで測り直した値です。

---

## 1. なぜこの形でしか検証できないか

実際の対話ログをいくら集めても、この診断の精度は測れません。
「この人の E017『比喩的思考』の真の値は 73 である」という**正解が存在しない**からです。
正解がなければ、出力が正しいかどうかを判定する手段がありません。

そこで問題を逆にします。

1. 100要素の真値 θ を**こちらで決めた**合成回答者を作る
2. その θ から確率的に証拠を生成し、**本番の `applyTurn` に流し込む**
3. 出てきたスコアが θ に戻るかを見る

これは心理測定や統計モデルで **パラメータ回復（parameter recovery）** と呼ばれる標準的な手法です。
自分で埋めた正解すら復元できない推定器は、埋めていない正解を復元できません。

### 検証を有利にしてある点（重要）

抽出側（Claude）は **誤りゼロの理想的な抽出器** として模擬しています。
捏造なし、取り違えなし、`strength` / `reliability` は正直な値。
ある要素についての証拠が肯定を向く確率はちょうど θ/100 です。

つまりここで出る誤差は **すべて `src/lib/engine` の計算式に由来** します。
実運用の精度はこれより悪くなることはあっても、良くなることはありません。
**測定結果は性能の上限値** であり、ここで見つかった問題はプロンプト改善では直りません。

### エンジンは再実装していない

`validation/lib/harness.ts` は `@/lib/engine/turnUpdate` の `applyTurn` を直接呼びます。
式をコピーして検証すると、コピーした式を検証しているだけになり、本体が変わっても気づけません。

`report.spec.ts` は毎回2つの不変条件を確認します。

- 40ターン回したあと、**全要素の score が「その要素の全証拠の事後平均」と一致する**
  （パイプラインのどこにも履歴の残りかすや経路依存がない）
- 同じ回答をシャッフルして流し直すと、**全要素の score が一致する**

`lib/estimators.ts` の `legacyRule` は修正前の加算式を凍結したコピーです。
比較のためだけに残してあり、`src/` の何も参照していません。

## 3. 何が成立していて、何が成立していないか

### ✅ 成立している：軸レベルの順序

10軸に集約した段階では、真値との相関 **r = 0.97**、ICC(1) = 0.79。
人物の違いが出力分散の 79% を占めており、レーダーチャートの**形**は本物です。

定数を振っても順位相関1.00（E7）、抽出が20ポイント肯定に傾いても増幅率0.28（E9）。
責務分離（LLMは抽出のみ、計算は純粋関数）の設計は、E9 の結果として現れています。
抽出のバイアスがスコアに素通りしない構造は、実際に効いていました。

なお増幅率は修正で 0.20 → 0.28 に上がりました。推定が証拠に忠実になったぶん、
抽出の偏りも素直に通るようになったということです。1.0 が「傾きをそのまま通す忠実な推定器」なので、
0.28 は依然として強く減衰させている側です。

### ✅ 直った：スコアの目盛りと一致性

E2 が最も重い結果でした。1要素あたりの証拠を増やしたときの挙動です。

| 証拠/要素 | 修正前 RMSE | 現在 RMSE | 修正前の0/100貼り付き | 現在 |
|---|---|---|---|---|
| 3.8 | 15.6点 | 15.2点 | 0% | 0% |
| 15 | 16.6点 | 10.3点 | 17% | 0% |
| 30 | 23.4点 | 8.4点 | 39% | 0% |
| 60 | 26.6点 | 6.2点 | 39% | 0% |
| 120 | 28.7点 | **4.7点** | 36% | **0%** |

修正前は**証拠が増えるほど誤差が増えて**いました。推定器は普通そうなりません。理由は式の形です：

```
delta = sign × strength × reliability × 12 × (1 − 0.5 × confidence)
```

この delta に **現在のスコアが入っていません**。スコアを引き戻す項がないので、
更新は「真値に近づく推定」ではなく「一定方向に進み続けるドリフト」でした。
肯定が否定よりわずかでも多ければスコアは100に向かって進み続け、止まりません
（減衰項は下限0.5なので速度が半分になるだけです）。
最終スコアは特性の強さではなく、その要素を何回聞いたかで決まっていました。
READMEの旧記録「30ターン→Score範囲 78.5〜100」は、この性質の実測値です。

現在は証拠が肯定を向く割合の事後平均になり、証拠120件で RMSE 4.7点まで収束します。

### ✅ 直った：順序不変性

E4。修正前は、同じ要素を繰り返し聞く条件で質問順を入れ替えると平均1.43点・最大9.18点動きました
（減衰項がその時点までの confidence に依存するため）。現在は和で定義されているので**厳密に0.00点**です。
`report.spec.ts` が全要素について毎回これを確認します。

### ✅ 直った：Confidenceの崩壊

E10。修正前は証拠を増やすと Confidence が 0.27 まで上がったあと **0.0009 まで落ちました**。

`detectDirectionalContradictions` は同一要素の肯定証拠×否定証拠を総当たりでペアにするため、
矛盾は証拠件数の2乗で増えます（証拠60件で1要素あたり約101件）。
未解決の矛盾ごとに `confidence × (1 − 0.25 × severity)` が掛かるので、101回掛ければ実質ゼロです。

ペナルティを (1) 重い上位3件まで、(2) `semantic` な矛盾のみ、に制限した結果、
現在は 0.26 → **0.72** と単調に上がります。終了条件 `conf ≥ 0.75` が要素単位では
到達可能な範囲に入りました（対話全体の平均はまだ届きません。理由は下の情報量の問題）。

### ✅ 直った：Confidenceのキャリブレーション

E3。Confidence帯ごとの平均絶対誤差は
0.2–0.4 → 11.5点(n=232)、0.4–0.6 → 9.4点(n=220)、0.6–0.8 → 5.7点(n=325)、0.8–1.0 → 2.1点(n=10)。
n≥20 の帯では単調に減少しており、Confidence は誤差の予測子として機能しています
（修正前は 21.5 → 12.8 → 17.0 → 18.9 で、高Confidence帯ほど誤差が**大きい**状態でした）。

0.4以上に達したサンプルの割合も 7.6% → **69.4%** に上がりました。
効いたのは矛盾ペナルティの二重計上をやめたことです。`directional` な矛盾——同一要素での
肯定×否定——は事後分散がすでに捉えており（割合が0.5付近＝分散最大）、そこへさらに割引を
掛けるのは同じ対立を2回数えることでした。中庸な特性（θが50付近）ほど肯定と否定が混ざるので、
最も情報が要る帯でちょうど Confidence が潰れていたことになります。
`semantic` な矛盾（別々の関連要素どうしの対立）は事後分布から見えないので、
引き続き割引の対象です。

### ❌ 直っていない：個人に対する断定

ここは式ではなく**設計の問題**なので、修正前後で1ミリも動いていません。

- **再検査信頼性 r = 0.23**（E5）。同じ人が2回受けると、同一要素で平均12.2点ずれます。
  心理測定の慣行では、個人について語るのに r ≥ 0.7、進路や採用の判断材料にするなら r ≥ 0.9 が要求されます。
  0.23 は「同じ人だと言えない」水準です。
- **要素レベルの相関 r = 0.46**（E1）＝真値の分散の21%しか説明していません。
- 原因は **情報量** です。30ターンで100要素を扱うと、1要素あたりの証拠は約2件。
  2件の観測から0〜100の量を推定することは、どんな手法でも不可能です。
  E8で確認済み：30ターンでは新旧どちらの式でも RMSE はほぼ同じ（16.5点 vs 15.8点）。

**更新式の修正が効くのは証拠が増えたときだけ**なので、残る手は証拠を増やすことです。
E11 でその配分を測りました。

### ✅ 一部改善：30ターンの使い方

E11。30ターンは約90回の「要素を1回聞く」に相当します。これを何要素に配るかの実測です
（軸の真値は、聞かなかった要素も含めた10要素の平均。「2要素の標本で軸を代表できるか」を問うため）。

| 対象要素数 | 証拠/要素 | 要素 r | 軸 r | 軸 RMSE |
|---|---|---|---|---|
| 100（旧） | 2 | 0.452 | 0.303 | 5.7点 |
| **60（採用）** | 3 | **0.504** | **0.442** | 5.6点 |
| 40 | 4.5 | 0.561 | 0.405 | 6.3点 |
| 20 | 9 | 0.685 | 0.351 | 7.5点 |
| 10 | 18 | 0.784 | 0.326 | 8.7点 |

**広く浅い探索は深さとのトレードオフではなく、単に劣っていました。**
60要素に絞ると要素相関も軸相関も同時に上がります。1要素あたり証拠2件では推定が雑音に
なりすぎて、それを集約する軸まで巻き添えになっていたためです。
さらに絞ると要素相関は上がり続けますが（10要素で r=0.78）、1軸あたりの要素が1つになるので
軸相関は落ちます。軸相関のピークが60要素なので、そこを採用しました。

`src/lib/ai/prompts.ts` に `FOCUS_ELEMENT_BUDGET = 60` を入れ、
60要素が開いたら新しい要素の提示をやめて既存を深掘りするようにしています。
同時に、未探索要素のタイブレークが `element_id` のアルファベット順だった問題も直しました
（毎回 E001→E090 の順に進み、AX10 は一度も測られないままでした）。
現在は最も手薄な軸から開きます。

この2つで E1 の要素相関 0.461→0.480、E5 の再検査信頼性 0.228→0.287、
E6 の軸相関 0.974→0.980・圧縮 3.5倍→3.1倍。改善幅は小さく、r=0.29 は依然として
「同じ人だと言える」水準ではありません。

### ⚠️ 出力幅の圧縮

E6。軸スコアの出力幅は真値の **1/3.5**（修正前は1/5.4）に圧縮されており、
10軸すべてが 40.9〜59.0点に収まります。

`src/components/AxisRadarChart.tsx:53` は `domain={[0, 100]}` の固定レンジで描いているので、
**ないものを見せてはいません**（軸ごとに目盛りを引き伸ばす実装なら、拡大された差を本物として
見せてしまうところでした）。その代わり、10軸すべてが中央付近に集まったほぼ正円が描かれ、
実在する差は見えません。`fillOpacity = 0.08 + 0.42 × meanConfidence`（同 45行目）も、
実測の meanConfidence が低いので常にごく薄くなります。

つまりレーダーチャートは「誤情報を与えない代わりに、情報も与えない」状態です。
順位表示に変えると、正しさを保ったまま情報量を回復できます。

## 4. 「実社会で評価されるか」への回答

検証できたことと、できないことを分けます。

### この検証で言えること

**現状の出力のうち、根拠があるのは「10軸の相対的な高低」までです。**

- 軸の順序 … 使える（r=0.97, ICC=0.79）
- 要素ごとの0〜100の数値 … 個人について語る根拠がない（再検査 r=0.23）
- Confidence の数値 … 誤差の予測子として機能する（帯が上がるほど誤差が減る）

これは「作り直し」を意味しません。**主張の強さを測定に合わせれば、そのまま成立します。**

| 現状の出し方 | 測定が支持する出し方 |
|---|---|
| E017: 78点 | 「この10軸のうち、AX02が相対的に高く出ています」 |
| Confidence 0.42 | そのまま使える。ただし何件の証拠に基づくかを併記する |
| 10軸のレーダー（41〜59点の範囲） | 順位またはパーセンタイルで表示する |

### この検証では言えないこと

- **構成概念妥当性**：100要素が本当に「創造性」を測っているか。
  この実験は「100要素に意味がある」と仮定した上で、その推定精度だけを見ています。
  要素の定義が妥当かは、外部指標との照合（既存の心理尺度、他者評価、実際の創作成果など）でしか
  検証できません。現状、外部指標との照合は一度も行われていません。**ここが最大の穴です。**
- **有用性**：ユーザーがこの結果を読んで役に立つと感じるか。これは測定精度とは別の問題で、
  精度が低くても「自分について考えるきっかけ」としての価値はありえます。ただしそれは
  「診断」ではなく「対話ツール」としての価値であり、名乗り方の問題になります。
- **SFCの評価**：これは検証の対象外です。ただし、AO入試で技術的な作品を出すときに
  「動きます」より強い主張は「限界を測定しました」であり、
  **この検証結果そのものが提出物として機能します**。E2やE10のような欠陥を自分で見つけて
  定量化し、直して、直った量まで測っている資料は、欠陥のないふりをした資料より説得力があります。

## 5. 残っている課題

測定結果から導かれる優先順位です。E列は該当実験。

1. **対話長を伸ばすか、要素スコアの公開をやめる**（E1, E5, E8, E11）— 最優先。
   探索を60要素に絞っても、1要素あたりの証拠は3件・再検査信頼性 r=0.29 止まりです。
   30ターンという上限がそもそも足りていません。要素スコアを個人に対して出すなら
   対話長を大幅に伸ばすか、対象を20要素程度まで絞る（軸の精度は落ちる）必要があります。
   現実的には**要素スコアを公開せず軸だけ出す**のが、いま測定が支持する唯一の選択です。
2. **表示を順序尺度に合わせる**（E5, E6）
   0〜100の絶対値をやめ、順位・パーセンタイル・「情報不足」の3段階にする。
3. **外部指標との照合**（構成概念妥当性）
   既存の心理尺度や他者評価と突き合わせる。ここだけはコードでは検証できません。

1と2は仕様の判断です。3は測定では原理的に埋められない穴です。

（矛盾ペナルティと事後分散の二重計上は解消済み。`Contradiction.kind` を追加し、
`directional` は Confidence を割り引かないようにしました。E3・E10 の改善はこれによるものです。）

## 6. この検証自体の限界

正直に書いておきます。

- **合成回答者は本物の人間ではありません。** θ/100 の確率で肯定証拠が出るという測定モデルは
  こちらが置いた仮定であり、実際の対話がこの形をしている保証はありません。
  ただしこの仮定は engine に有利な側（誤差なし・偏りなし）に置いてあります。
- **質問選択はLLMではなく近似です。** 実際の QValue のうち支配的な項（不確実性 0.35＋未探索 0.10）を
  再現していますが、矛盾解消項や多様性項の挙動は含まれていません。
- **要素間の相関を入れていません。** 実際の人間の特性は相関しますが、本実装も要素を独立に扱っている
  （`related_elements` はスコア伝播に使わないと README に明記）ため、条件は揃っています。
- **E2/E4/E10 の深掘り条件（8要素に集中）は現行アプリの動作ではありません。**
  これは推定器の漸近的な性質を見るための条件です。「今のアプリでこうなる」ではなく
  「証拠を増やす方向に改善したときにこうなる」と読んでください。
- **修正の効果は同じ合成モデル上で測ったものです。** 実際の対話で RMSE が 4.7点になるという
  主張ではありません。「同じ条件で比べると旧式は発散し、新式は収束する」という比較の主張です。
