# 測定モデルとしての検証（validation/）

このディレクトリは、`src/lib/engine` を **測定器として** 検証するための実験一式です。
アプリが動くかではなく、**アプリが出す数字が何かを測っているか** を調べます。

```bash
npm run validate     # 10実験を実行し validation/report/ に出力（約20秒・API不要）
```

---

## 1. なぜこの形でしか検証できないか

実際の対話ログをいくら集めても、この診断の精度は測れません。
「この人の E017『比喩的思考』の真の値は 73 である」という**正解が存在しない**からです。
正解がなければ、出力が正しいかどうかを判定する手段がありません。

そこで問題を逆にします。

1. 100要素の真値 θ を**こちらで決めた**合成回答者を作る
2. その θ から確率的に証拠を生成し、**本番の `applyTurn` に流し込む**
3. 出てきたスコアが θ に戻るかを見る

これは心理測定や統計モデルで **パラメータ回復（parameter recovery）** と呼ばれる標準的な手法です。
自分で埋めた正解すら復元できない推定器は、埋めていない正解を復元できません。

### 検証を有利にしてある点（重要）

抽出側（Claude）は **誤りゼロの理想的な抽出器** として模擬しています。
捏造なし、取り違えなし、`strength` / `reliability` は正直な値。
ある要素についての証拠が肯定を向く確率はちょうど θ/100 です。

つまりここで出る誤差は **すべて `src/lib/engine` の計算式に由来** します。
実運用の精度はこれより悪くなることはあっても、良くなることはありません。
**測定結果は性能の上限値** であり、ここで見つかった問題はプロンプト改善では直りません。

### エンジンは再実装していない

`validation/lib/harness.ts` は `@/lib/engine/turnUpdate` の `applyTurn` を直接呼びます。
式をコピーして検証すると、コピーした式を検証しているだけになり、本体が変わっても気づけません。
定数を振る実験のためだけにパラメータ化した複製が `lib/estimators.ts` にありますが、
`report.spec.ts` が本番の `evidenceDelta` と 2000 ケースで一致することを毎回確認します。

## 3. 何が成立していて、何が成立していないか

### ✅ 成立している：軸レベルの順序

10軸に集約した段階では、真値との相関 **r = 0.97**、ICC(1) = 0.77。
人物の違いが出力分散の 77% を占めており、レーダーチャートの**形**は本物です。
定数を ±25% 振っても順位相関 0.99 以上（E7）、抽出が20ポイント肯定に傾いても
偏りは4点しか動かない（E9）。**順序尺度としては機能しています。**

責務分離（LLMは抽出のみ、計算は純粋関数）の設計は、E9 の結果として現れています。
抽出のバイアスがスコアに素通りしない構造は、実際に効いていました。

### ❌ 成立していない：個人に対する断定

- **再検査信頼性 r = 0.23**（E5）。同じ人が2回受けると、同一要素で平均8.8点ずれます。
  心理測定の慣行では、個人について語るのに r ≥ 0.7、進路や採用の判断材料にするなら r ≥ 0.9 が要求されます。
  0.23 は「同じ人だと言えない」水準です。
- **要素レベルの相関 r = 0.46**（E1）＝真値の分散の21%しか説明していません。
  「常に50と答えるモデル」の RMSE 17.7点に対し、実際は 15.8点。2点しか勝っていません。
- 原因は式ではなく **情報量** です。30ターンで100要素を扱うと、1要素あたりの証拠は約2件。
  2件の観測から0〜100の量を推定することは、どんな手法でも不可能です（E8で確認：
  正しい推定式に差し替えても、30ターンのままでは改善しません）。

### ❌ 成立していない：スコアの目盛り

E2 が最も重い結果です。1要素あたりの証拠を 3.8件 → 120件 に増やすと：

| 証拠/要素 | 現行式 RMSE | 事後平均式 RMSE | 0か100に貼り付いた割合 |
|---|---|---|---|
| 3.8 | 15.6点 | 15.2点 | 0% |
| 15 | 18.2点 | 10.3点 | 19% |
| 60 | 27.4点 | 6.2点 | 45% |
| 120 | 27.0点 | 4.7点 | 36% |

**証拠が増えるほど誤差が増えます。** 推定器は普通そうなりません。理由は式の形にあります：

```
delta = sign × strength × reliability × 12 × (1 − 0.5 × confidence)
```

この delta に **現在のスコアが入っていません**。スコアを引き戻す項がないので、
更新は「真値に近づく推定」ではなく「一定方向に進み続けるドリフト」です。
肯定が否定よりわずかでも多ければ、スコアは 100 に向かって進み続け、止まりません
（減衰項は下限 0.5 なので速度が半分になるだけです）。

結果として、最終スコアは**特性の強さではなく、その要素を何回聞いたかで決まります**。
READMEの動作確認記録にある「30ターン→Score範囲 78.5〜100」は、この性質の実測値です。

同じ証拠を事後平均式（`lib/estimators.ts` の `posteriorRule`）で読むと RMSE は 4.7点まで下がるので、
**証拠が足りないのではなく、読み方の問題**であることが分かります（証拠が十分ある場合に限る）。

ただし順位相関は 0.91 を保ちます。**壊れているのは目盛りであって、並び順ではありません。**

### ❌ 成立していない：Confidence の意味

E10。証拠を増やすと Confidence は 0.27 まで上がったあと **0.0009 まで落ちます**。

`detectDirectionalContradictions` は同一要素の肯定証拠×否定証拠を総当たりでペアにするため、
矛盾は証拠件数の2乗で増えます（証拠60件で1要素あたり約101件）。
未解決の矛盾ごとに `confidence × (1 − 0.25 × severity)` が掛かるので、
100回掛ければ実質ゼロです。

副作用が2つあります。

1. **終了条件 `conf ≥ 0.75` は、対話を延ばすほど遠のきます。** 30ターン強制終了は事実上の唯一の出口です。
   READMEの実装判断ログ #2 で「Confidence 0.019 で終了してしまう」問題に気づき最低値0.25を設けていますが、
   原因は飽和判定ではなくこちらにあります。
2. **矛盾ペナルティで confidence が下がると、減衰項 `1 − 0.5×conf` が1に近づき、スコアのドリフトが最高速になります。**
   2つの不具合が互いを増幅しています。

キャリブレーション（E3）も単調ではありません。誤差が最小なのは Confidence 0.2–0.4 の帯（12.8点）で、
0.4–0.6 では 17.0点、0.6–0.8 では 18.9点と**増えます**。
そして Confidence が 0.4 を超えたサンプルは全体の 7%。
「Confidence が高い軸は信頼してよい」という画面上の約束は、ほとんど検証されない領域にあります。

### ⚠️ 順序不変性は「たまたま」成立している

E4。現行の質問選択は毎ターン最も不確実な要素を選ぶため、1つの要素は事実上1回しか聞かれません。
そのため質問順を入れ替えてもスコアは**まったく変わりません**（差 0.00点）。

しかし同じ要素を繰り返し聞く条件では、順序を変えるだけで平均1.43点・最大9.18点動きます。
減衰項がその時点までの confidence に依存するためです。
つまり順序不変性は設計で保証されているのではなく、**要素を掘り下げていないから成立している**だけです。
深掘りする方向に改善すると、この性質は失われます。

## 4. 「実社会で評価されるか」への回答

検証できたことと、できないことを分けます。

### この検証で言えること

**現状の出力のうち、根拠があるのは「10軸の相対的な高低」までです。**

- 軸の順序 … 使える（r=0.97, ICC=0.77）
- 要素ごとの0〜100の数値 … 個人について語る根拠がない（再検査 r=0.23）
- Confidence の数値 … 現状は証拠の多さの指標ですらなく、矛盾の多さで潰れる

これは「作り直し」を意味しません。**主張の強さを測定に合わせれば、そのまま成立します。**

| 現状の出し方 | 測定が支持する出し方 |
|---|---|
| E017: 78点 | 「この10軸のうち、AX02が相対的に高く出ています」 |
| Confidence 0.42 | 証拠の件数と種類数をそのまま表示する |
| 10軸のレーダー（44〜56点の範囲） | 順位またはパーセンタイルで表示する |

E6 で分かったことがもう一つあります。軸スコアの出力幅は真値の **5.4分の1** に圧縮されており、
10軸すべてが 44〜56点に収まります。

`src/components/AxisRadarChart.tsx:53` は `domain={[0, 100]}` の固定レンジで描いているので、
**ないものを見せてはいません**（軸ごとに目盛りを引き伸ばす実装なら、5.4倍に拡大された差を
本物として見せてしまうところでした）。その代わり、10軸すべてが中央付近に集まった
ほぼ正円が描かれ、実在する差は見えません。`fillOpacity = 0.08 + 0.42 × meanConfidence`
（同 45行目）も、実測の meanConfidence がほぼ 0 なので常に最小の薄さになります。

つまり現状のレーダーチャートは「誤情報を与えない代わりに、情報も与えない」状態です。
順位表示に変えると、正しさを保ったまま情報量を回復できます。

### この検証では言えないこと

- **構成概念妥当性**：100要素が本当に「創造性」を測っているか。
  この実験は「100要素に意味がある」と仮定した上で、その推定精度だけを見ています。
  要素の定義が妥当かは、外部指標との照合（既存の心理尺度、他者評価、実際の創作成果など）でしか検証できません。
  現状、外部指標との照合は一度も行われていません。
- **有用性**：ユーザーがこの結果を読んで役に立つと感じるか。これは測定精度とは別の問題で、
  精度が低くても「自分について考えるきっかけ」としての価値はありえます。ただしそれは
  「診断」ではなく「対話ツール」としての価値であり、名乗り方の問題になります。
- **SFCの評価**：これは検証の対象外です。ただし、AO入試で技術的な作品を出すときに
  「動きます」より強い主張は「限界を測定しました」であり、
  **この検証結果そのものが提出物として機能します**。E2やE10のような欠陥を自分で見つけて
  定量化している資料は、欠陥のないふりをした資料より説得力があります。

## 5. 直すなら、どの順か

測定結果から導かれる優先順位です。E列は該当実験。

1. **矛盾ペナルティの上限**（E10）
   総当たりで生成される矛盾を全部掛けるのをやめ、要素あたり上位k件（k=3程度）に制限するか、
   `min(penalty, floor)` で下限を設ける。現状は終了条件が到達不能になっています。
2. **スコア更新式に引き戻し項を入れる**（E2）
   `lib/estimators.ts` の `posteriorRule` が候補です。証拠の重み付き比率として書けば、
   一致性・順序不変性・Confidenceの定義（事後分散）が同時に手に入ります。
   同じ証拠で RMSE 27.0点 → 4.7点。
3. **要素数か対話長のどちらかを変える**（E1, E8）
   1要素あたり証拠2件では、式を直しても要素スコアは意味を持ちません。
   100要素を維持するなら要素スコアを公開せず軸だけ出す、
   要素スコアを出すなら対象を20要素程度に絞る、のどちらかです。
4. **表示を順序尺度に合わせる**（E5, E6）
   0〜100の絶対値をやめ、順位・パーセンタイル・「情報不足」の3段階にする。

1と2は `src/lib/engine` の局所的な変更で、既存の105ケースのテストが回帰を検出できます。
3と4は仕様の判断です。

## 6. この検証自体の限界

正直に書いておきます。

- **合成回答者は本物の人間ではありません。** θ/100 の確率で肯定証拠が出るという測定モデルは
  こちらが置いた仮定であり、実際の対話がこの形をしている保証はありません。
  ただしこの仮定は現行式に有利な側（誤差なし・偏りなし）に置いてあります。
- **質問選択はLLMではなく近似です。** 実際の QValue のうち支配的な項（不確実性 0.35＋未探索 0.10）を
  再現していますが、矛盾解消項や多様性項の挙動は含まれていません。
- **要素間の相関を入れていません。** 実際の人間の特性は相関しますが、本実装も要素を独立に扱っている
  （`related_elements` はスコア伝播に使わないと README に明記）ため、条件は揃っています。
- **E2/E4/E10 の深掘り条件（8要素に集中）は現行アプリの動作ではありません。**
  これは推定器の漸近的な性質を見るための条件です。「今のアプリでこうなる」ではなく
  「証拠を増やす方向に改善したときにこうなる」と読んでください。
